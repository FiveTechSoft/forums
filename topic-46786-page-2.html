Dear Jimmy,

Thanks for testing Harbour 4! Answers to your four points, checked against the current main branch:

1. File-scope STATIC

Confirmed: file-wide STATIC variables are not in this increment yet (global storage needs its own design). STATIC inside a function works and keeps its value between calls:

Code: Select all Collapse
function main()
    STATIC n := 0
    n := n + 1
    ? n    // 1 (and keeps its value between calls)
return nil

2. PRIVATE a := 800/2

This works in current main (prints 400). Scoped PRIVATE/PUBLIC support landed on 15 November, while the binaries linked in this thread (v0.9.0) date from 14 November. Release v0.11.2 already includes it:
https://github.com/FiveTechSoft/HarbourRust/releases/tag/v0.11.2

Which build are you using? If it's the v0.9.0 download, that would explain the error.

3. #include "fivewin.ch"

Includes are supported. Quoted includes are searched first next to the .prg that contains them, then in every -I directory. Angle-bracket includes search only -I directories. Example:

Code: Select all Collapse
hbc main.prg main.exe -I C:\fwh\include

If it still fails, please share your exact command line and where fivewin.ch lives. Note: finding the header does not establish FiveWin GUI compatibility - the GUI runtime is not in the current language subset.

4. More than one file

hbc accepts one input PRG per invocation (multi-module linking is not in this increment). Two ways work today:

a) Textual inclusion of another PRG:

Code: Select all Collapse
// main.prg
#include "lib.prg"

function main()
    ? greet()    // defined in lib.prg
return nil

b) The tools\hbld.ps1 helper in the repository checkout concatenates modules + main and compiles the result. Run from the repository root, with your PRG files and the downloaded hbc_0.11.2.exe there:

Code: Select all Collapse
powershell -ExecutionPolicy Bypass -File tools\hbld.ps1 -Main inv_main.prg -Modules inv_data.prg,inv_report.prg -Out inv_app.exe -Hbc .\hbc_0.11.2.exe

Functions from the modules are called normally, no EXTERNAL needed.

Dear Enrico,

Confirmed, and thank you for the clear report. #pragma BEGINDUMP / #pragma ENDDUMP is not supported yet: hbc has no integrated C stage. The compiler recognizes both pragmas and stops with an explicit error pointing to the supported path, instead of miscompiling:

Code: Select all Collapse
error: line 4: #pragma BEGINDUMP (embedded C) is not supported: hbc has no C stage; put the C in a separate file compiled with a C compiler and link it through the Extend bridge (docs/EXTEND-BRIDGE.md)

What works today, along the lines of Daniel's suggestion of keeping the C in separate files:

1. The Extend bridge (docs/EXTEND-BRIDGE.md): declare the functions EXTERNAL in the PRG, write them as HB_FUNC in a separate .c against our bridge header, compile both and link. There is a working demo in the tree (extend/demo), just verified on current main: builds and runs clean.

2. The tools/hbc_hbmk2.py adapter automates that flow (one .prg plus .c/.o, compiled with gcc and linked through the official hbmk2). Linux x86-64 only for now; on Windows the manual MinGW recipe in docs/EXTEND-BRIDGE.md applies.

Full BEGINDUMP/ENDDUMP support (extract the C blocks, compile them separately and link through the bridge) is on the public roadmap (docs/ROADMAP.md). No date promised, but your report is exactly the use case it is meant to cover.

One honest caveat: the bridge ABI is intentionally scoped, so arbitrary Harbour/FiveWin C libraries will not drop in unchanged.

Dear Jimmy,

1. The two ZIP files are source-code snapshots:

  • HarbourRust-main.zip follows the main development branch, so its contents change as we push updates.
  • HarbourRust-0.11.2.zip is the source snapshot for the fixed v0.11.2 release.

For a ready-to-run Windows compiler, download hbc_0.11.4.exe from the release page rather than relying on the bin/hbc.exe snapshot inside a source ZIP:
https://github.com/FiveTechSoft/HarbourRust/releases/tag/v0.11.4

2. First extract the source ZIP to a normal folder. The official v0.11.2 archive contains HarbourRust-0.11.2\tests\samples\multi\ directly, without an extra HarbourRust-0.10.0 folder.

Put hbc_0.11.4.exe in the extracted repository root (the folder containing tools and tests), open CMD in that folder, and run this as one line:

Code: Select all Collapse
powershell -ExecutionPolicy Bypass -File tools\hbld.ps1 -Main tests\samples\multi\inv_main.prg -Modules tests\samples\multi\inv_data.prg,tests\samples\multi\inv_report.prg -Out inv_app.exe -Hbc .\hbc_0.11.4.exe

Then run:

Code: Select all Collapse
inv_app.exe

The sample prints three stock items, totals of 2 in stock and 1 out of stock, then the sequence 1 2 3 from a function-local STATIC counter.

One important limit: hbld.ps1 combines the three PRGs into one temporary source file before compiling. It is a working build helper, not separate compilation or a multi-module linker yet.

Harbour 4 – Why Not Start with a Useful New Module?

I have been thinking again about Harbour 4.
One of the biggest problems with many Harbour/FiveWin applications is still shared DBF access over a network.
Even with desktop applications, SMB access, record locking and network interruptions can cause problems. And for web applications, direct DBF file access from the browser is not possible.

This is why we developed a small Harbour microservice that handles DBF access centrally through HTTP/JSON.
Wouldn't it make sense to offer such a microservice as one of the first new modules for Harbour 4?
There are three clear advantages:

  1. Central DBF access: Reading, writing and record locking through one service instead of many direct SMB connections.
  2. Desktop and Web: Existing FiveWin applications could use the service, and new web applications could access the same data.
  3. Protecting existing investments: DBF/CDX files and existing business logic can remain unchanged. There is no need to rewrite the whole application.

Just remember the move from Clipper to Harbour. How many years did that take?
A new compiler or language version alone may not convince many developers to change their working applications, especially if there is no immediate benefit.

A microservice, on the other hand, would simply be an additional module.
Developers could use it where it makes sense, without changing their compiler or rewriting their applications.
From a marketing point of view, this could also be interesting.

Harbour 4 could offer something useful from the beginning, solving a problem that many xBase developers already know.
And perhaps the microservice could even be made available before Harbour 4 is finished.
This would give developers a practical improvement today, while allowing them to modernize their applications step by step.

hbnetio: remote tables and RPC in Harbour

hbnetio is a Harbour contrib (contrib/hbnetio) that implements NETIO, Harbour's own network protocol over TCP. It does two things:

  1. Remote file and table access. A NETIO server publishes a folder, and clients open DBF files, indexes, memos and so on over TCP instead of through a Windows shared drive (SMB). You use a path prefix: net:server:port:/path. For example:

    Code: Select all Collapse
    USE "net:192.168.1.10:2941:/data/customers"

  2. Remote procedure calls (RPC). A client can run functions on the server and get the result back. There are also data streams for sending messages.

What it is for

  • Reliability and performance with DBF over a network. It avoids many typical SMB problems, such as oplocks, network caching and index corruption.

  • Access over the internet or a VPN. It works over a single TCP port.

  • Security. It supports a password and compression, plus an RPC filter to limit which functions can be called.

Main functions

  • Server: netio_Listen(), netio_Server() and netio_MTServer() start the server and handle connections. netio_RPCFilter() restricts the allowed RPC functions.

  • Client: netio_Connect() and netio_Disconnect() manage the connection. netio_ProcExists(), netio_ProcExec() and netio_FuncExec() run procedures or functions on the server. netio_OpenItemStream() and netio_OpenDataStream() open data streams.

Basic usage

Include hbnetio.ch and link with hbnetio.hbc. Harbour also ships a ready-made server (hbnetio, in contrib/hbnetio/utils) that you can run directly.

Two modes, two behaviours

NETIO is not an SQL server, and it helps to keep its two modes apart:

  • File access with net: only file operations travel over the network, so indexes and filters are still processed on the client. You gain reliability and control over access, not necessarily speed on heavy queries.

  • RPC with netio_FuncExec() the function runs on the server, opens the tables locally (no network in between) and returns only the result, for example an array or a hash. This is how you move heavy logic (reports, aggregates, searches) next to the data.

Both modes can be combined in the same application.

Example: server

Code: Select all Collapse
// Module: srvnetio.prg   Version: 1.0
// Minimal NETIO server: publishes the /data folder and allows RPC.
// Build with: hbmk2 srvnetio.prg hbnetio.hbc

#include "hbnetio.ch"

REQUEST DBFCDX              // RDD that will be used on the server

PROCEDURE Main()
   LOCAL pListen            // pointer to the listening socket

   // Start the multithreaded server:
   // port, interface (0.0.0.0 = all), published root folder,
   // RPC enabled (.T. = any linked function), access password
   pListen := netio_MTServer( 2941, "0.0.0.0", "/data", .T., "pass123" )

   IF Empty( pListen )
      ? "Could not start the NETIO server"
      RETURN
   ENDIF

   ? "NETIO server running on port 2941. Press a key to stop..."
   Inkey( 0 )

   // Close the listening socket
   netio_ServerStop( pListen )

   RETURN

// Function the client can run through RPC
FUNCTION SrvDateTime()
   RETURN DToC( Date() ) + " " + Time()

Example: client

Code: Select all Collapse
// Module: clinetio.prg   Version: 1.0
// Minimal NETIO client: opens a remote DBF and calls an RPC function.
// Build with: hbmk2 clinetio.prg hbnetio.hbc

#include "hbnetio.ch"

REQUEST DBFCDX

PROCEDURE Main()
   LOCAL lOk          // connection result
   LOCAL cDateTime    // RPC result

   rddSetDefault( "DBFCDX" )

   // Connect: server, port, timeout (NIL = default), password
   lOk := netio_Connect( "127.0.0.1", 2941, , "pass123" )

   IF ! lOk
      ? "Could not connect to the server"
      RETURN
   ENDIF

   // 1) Remote table access: the net: prefix uses the active connection.
   //    The path is relative to the published root folder (/data)
   USE "net:/customers" SHARED NEW
   IF ! NetErr()
      ? "Records in customers:", LastRec()
      USE
   ENDIF

   // 2) RPC: check that the function exists, then run it on the server
   IF netio_ProcExists( "SrvDateTime" )
      cDateTime := netio_FuncExec( "SrvDateTime" )
      ? "Server date and time:", cDateTime
   ENDIF

   netio_Disconnect( "127.0.0.1", 2941 )

   RETURN

Notes

  • net: without a server uses the last connection made with netio_Connect(). You can also be explicit: USE "net:127.0.0.1:2941:/customers"

  • With .T. as the RPC parameter, the client can call any function linked into the server. In production, use netio_RPCFilter() or a list of allowed functions instead.

  • With net: file access, CDX indexes are processed on the client, so performance depends on the network, just as it does with SMB. With RPC, the work is done on the server.

  • If the server keeps using DBF, you keep its limits: no real ACID transactions and a risk of corruption on a crash. RPC does not change that, only the storage engine does.

Comments and corrections are welcome.

Harbour 4 – Why Not Start with a Small Microservice?

This is exactly my point. New versions take time to reach developers, especially when their existing applications are working well.

That is why I suggested a small Harbour microservice as a practical module for Harbour 4.

Our concept is designed for small businesses and developers like us, often working alone or in small teams.

The idea is simple:

PHP sends an HTTP request with JSON data over a short Winsock connection.

The microservice calls an existing Harbour function using hb_vmDo().

The function returns JSON, and the connection is closed.

No permanent connections, no special database protocol.

Long-running tasks are handled by separate Harbour worker EXEs. If necessary, Apache can distribute requests across several microservice instances.

We keep our existing Harbour business logic and DBF/CDX files. HTML and JavaScript provide the new web interface.

Why did I suggest this for Harbour 4?

Because it could be a small, useful module that developers can start experimenting with immediately, without changing their compiler or rewriting their applications.

Learning by doing.

Harbour 4 could support exactly this approach and give smaller developers a simple way to explore web development with their existing Harbour knowledge.

No large framework, no unnecessary overhead. Just a small tool that everyone can understand and extend.
