Estimado Antonio,

Gracias por la pregunta. Te dejo una estructura de trabajo para destilar un modelo, de menos a más esfuerzo, con ejemplos. Aviso importante: los ejemplos de código de este mensaje NO los he ejecutado; son esquemas para entender el flujo y habrá que ajustarlos (versiones de librerías, nombres de campos, memoria de GPU) antes de usarlos.

1. Definir el objetivo antes de tocar nada

  • Qué modelo es el profesor (teacher) y qué tamaño/coste debe tener el alumno (student): latencia, memoria, dispositivo de destino.
  • Qué tarea concreta debe conservar el alumno (por ejemplo, responder dudas de FiveWin/Harbour, clasificar, resumir). Un alumno pequeño no puede igualar al profesor en todo: se destila para una tarea o un dominio.
  • Qué métrica dirá que ha funcionado (precisión en un conjunto de prueba propio, % de respuestas correctas, latencia, coste por consulta).

2. Elegir el tipo de destilación

  • Destilación por respuestas (la más sencilla y la más usada): el profesor genera respuestas a un conjunto de prompts y el alumno se entrena (fine-tuning supervisado) con esos pares prompt/respuesta. Funciona aunque profesor y alumno tengan tokenizadores distintos.
  • Destilación por logits (clásica, Hinton et al. 2015): el alumno aprende a imitar la distribución de probabilidades del profesor, no solo la palabra elegida. Da más señal, pero necesita acceso a los logits y que ambos modelos compartan el vocabulario (o una correspondencia entre tokenizadores).
  • Variantes: usar también capas intermedias, o entrenar con respuestas generadas por el propio alumno y corregidas por el profesor (on-policy), que suele corregir el desajuste entre entrenamiento y uso real.

3. Preparar los datos

  • Reunir prompts representativos del uso real (preguntas reales de usuarios, anonimizadas), no solo ejemplos fáciles. Entre unos miles y decenas de miles suele bastar para una tarea acotada.
  • Reservar desde el principio un conjunto de evaluación que no se use jamás para entrenar, y revisar a mano una muestra.
  • Generar las respuestas con el profesor, con temperatura baja o media, y filtrar: quitar respuestas vacías, duplicadas, demasiado largas o que no cumplen el formato. Con código, ejecutar o compilar y descartar lo que falla.
  • Revisar licencias: los términos de uso de algunos modelos comerciales prohíben usar sus salidas para entrenar otros modelos. Hay que comprobarlo antes de generar datos con ellos.

Ejemplo de generación (sin probar), con la librería transformers:

Code: Select all Collapse
# Esquema NO probado: genera respuestas con el modelo profesor
import json
from transformers import AutoTokenizer, AutoModelForCausalLM

teacher_id = "NOMBRE_DEL_PROFESOR"          # a elegir
tok = AutoTokenizer.from_pretrained(teacher_id)
teacher = AutoModelForCausalLM.from_pretrained(teacher_id, device_map="auto")

prompts = [l.strip() for l in open("prompts.txt", encoding="utf-8") if l.strip()]
with open("destilado.jsonl", "w", encoding="utf-8") as out:
    for p in prompts:
        msgs = [{"role": "user", "content": p}]
        ids = tok.apply_chat_template(msgs, add_generation_prompt=True,
                                      return_tensors="pt").to(teacher.device)
        gen = teacher.generate(ids, max_new_tokens=512, do_sample=True, temperature=0.3)
        resp = tok.decode(gen[0][ids.shape[1]:], skip_special_tokens=True)
        out.write(json.dumps({"prompt": p, "response": resp}, ensure_ascii=False) + "\n")

Para volumen real conviene un servidor de inferencia (por ejemplo vLLM) en lugar de generar de uno en uno.

4. Entrenar el alumno

  • Partir de un modelo base pequeño ya preentrenado (misma familia que el profesor si se destilan logits). Entrenar desde cero casi nunca compensa.
  • Para pocos recursos: ajuste con LoRA/QLoRA (librería peft) en lugar de reentrenar todos los pesos.
  • Hiperparámetros de partida: 1 a 3 épocas, tasa de aprendizaje baja (del orden de 1e-5 a 2e-4 según sea LoRA o completo), y vigilar la pérdida en el conjunto de evaluación para parar si empieza a empeorar (sobreajuste).

Ejemplo de ajuste supervisado con las respuestas del profesor (sin probar; la API de trl cambia entre versiones):

Code: Select all Collapse
# Esquema NO probado: SFT con trl sobre destilado.jsonl
from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

ds = load_dataset("json", data_files="destilado.jsonl")["train"]
ds = ds.map(lambda r: {"messages": [
    {"role": "user", "content": r["prompt"]},
    {"role": "assistant", "content": r["response"]}]})

cfg = SFTConfig(output_dir="alumno", num_train_epochs=2, learning_rate=1e-4,
                per_device_train_batch_size=4, gradient_accumulation_steps=8)
trainer = SFTTrainer(model="NOMBRE_DEL_ALUMNO", args=cfg, train_dataset=ds)
trainer.train()
trainer.save_model("alumno")

5. Pérdida por logits (si se destila con logits)
La pérdida habitual combina dos términos: la divergencia KL entre las distribuciones suavizadas con temperatura T del profesor y del alumno, y la entropía cruzada normal contra la etiqueta real. Se multiplica el término KL por T al cuadrado para mantener la escala de los gradientes.

Code: Select all Collapse
# Esquema NO probado: pérdida de destilación (Hinton et al., 2015)
import torch.nn.functional as F

def kd_loss(logits_alumno, logits_profesor, etiquetas, T=2.0, alpha=0.5):
    kl = F.kl_div(F.log_softmax(logits_alumno / T, dim=-1),
                  F.softmax(logits_profesor / T, dim=-1),
                  reduction="batchmean") * (T * T)
    ce = F.cross_entropy(logits_alumno.view(-1, logits_alumno.size(-1)),
                         etiquetas.view(-1), ignore_index=-100)
    return alpha * kl + (1 - alpha) * ce

Ojo: en modelos de lenguaje los logits tienen forma (lote, secuencia, vocabulario); hay que aplicar el KL token a token ignorando el relleno, y el profesor debe ir en modo evaluación y sin gradientes.

6. Evaluar

  • Comparar siempre tres cosas sobre el mismo conjunto de evaluación: el profesor, el alumno base sin entrenar y el alumno destilado. Si el destilado no supera al base, no ha servido.
  • Métricas objetivas cuando existan (código que compila, respuestas con formato correcto, exactitud en clasificación) y revisión humana de una muestra para el resto. Si se usa otro modelo como juez, comprobar su sesgo con una muestra revisada a mano.
  • Pruebas fuera de dominio para ver qué se ha olvidado, y casos de seguridad.
  • Herramienta habitual para pruebas estándar: lm-evaluation-harness.

7. Iterar y desplegar

  • Mirar dónde falla el alumno, añadir prompts de esos casos y repetir (suele valer más mejorar los datos que cambiar hiperparámetros).
  • Para desplegar: fusionar LoRA, cuantizar (por ejemplo a 4 u 8 bits) y servir con llama.cpp/GGUF o vLLM. Volver a medir tras cuantizar, porque pierde algo de calidad.

Resumen del flujo
Objetivo y métrica, conjunto de evaluación aparte, prompts reales, respuestas del profesor filtradas, ajuste del alumno (LoRA si hay poca GPU), comparar profesor / alumno base / alumno destilado, corregir los datos y repetir.

Si queréis, puedo adaptar el esquema a un caso concreto (por ejemplo un asistente para dudas de FiveWin) indicando el modelo profesor, el alumno y los recursos disponibles. Los ejemplos de código habría que probarlos en vuestro entorno antes de fiarse de ellos.

Estimado Antonio,

Va un plan concreto para un asistente de dudas de FiveWin y Harbour, por fases. Igual que antes: los fragmentos de código son esquemas que NO he ejecutado; hay que probarlos y ajustarlos. Y es un plan de trabajo, no un compromiso de producto de nadie.

Fase 0. Alcance y reglas

  • Objetivo: responder dudas habituales (diálogos, controles, bases de datos, compilación, errores típicos) con respuestas cortas y código que compile.
  • Fuentes permitidas: solo material público. Documentación publicada, posts públicos del foro (respetando autoría y sin datos personales), manuales y ejemplos publicados, y el código fuente público de Harbour. Nada que no sea público, ni código interno, ni repositorios privados.
  • Métrica de éxito desde el día uno: porcentaje de respuestas correctas sobre un conjunto de preguntas reales, y porcentaje de ejemplos de código que compilan.

Fase 1. Corpus

  1. Exportar los hilos públicos del foro en formato pregunta, respuestas, y marcar cuál respuesta resolvió el problema (la que el autor aceptó o la que mejor encaja).
  2. Quitar nombres, correos, IPs y cualquier dato personal. Guardar la URL del hilo como fuente para poder citarla.
  3. Separar aparte entre 200 y 500 preguntas reales como conjunto de evaluación y no tocarlas nunca durante el entrenamiento.
  4. Normalizar el código a un estilo único y eliminar fragmentos rotos o de versiones muy antiguas, o etiquetarlos con la versión.

Formato de cada registro (JSON por línea):

Code: Select all Collapse
{"pregunta": "¿Cómo pongo el foco en un GET al abrir un diálogo?",
 "respuesta": "Texto de la respuesta...",
 "version": "FWH 2x.xx / Harbour 3.2",
 "fuente": "URL pública del hilo"}

Fase 2. Datos sintéticos con un profesor

  • Un modelo grande (el profesor) recibe cada pregunta junto con los trozos de documentación pública más relacionados (recuperación por similitud) y redacta la respuesta citando la fuente.
  • Se piden respuestas con un formato fijo: explicación breve, código, y qué versión aplica.
  • Filtro automático: se extrae el código de cada respuesta y se comprueba que compila con el compilador de Harbour en modo solo sintaxis. Lo que no compila se descarta o se manda a revisión.

Esquema del filtro (sin probar):

Code: Select all Collapse
# Esquema NO probado: comprobar que el código Harbour de una respuesta compila
import re, subprocess, tempfile, os

def extrae_codigo(texto):
    return re.findall(r"\[code\](.*?)\[/code\]", texto, flags=re.S)

def compila(prg):
    with tempfile.TemporaryDirectory() as d:
        ruta = os.path.join(d, "t.prg")
        open(ruta, "w", encoding="utf-8").write(prg)
        r = subprocess.run(["harbour", ruta, "-s", "-q0"], capture_output=True, text=True)
        return r.returncode == 0

Ojo con dos cosas: el código con comandos de FiveWin necesita los ficheros de cabecera (.ch) y la ruta de include, así que habría que pasar las opciones -I correspondientes; y comprobar sintaxis no garantiza que el código haga lo que dice.

Fase 3. Entrenamiento

  • Modelo base: uno pequeño o mediano que ya sepa programar (valen modelos abiertos de código); el alumno se ajusta con LoRA, que cabe en una GPU modesta.
  • Mezclar los datos de FiveWin con una parte de datos generales de programación para que no olvide lo básico.
  • Mejor entrenar con las respuestas ya filtradas que con cantidad: unos pocos miles de ejemplos buenos suelen dar más que decenas de miles dudosos.

Fase 4. Evaluación

  • Comparar tres casos sobre las preguntas reservadas: el modelo base sin entrenar, el modelo base con recuperación de documentación (sin entrenar) y el modelo destilado.
  • Medir: respuestas correctas (revisión humana de una muestra), código que compila, y casos en que inventa funciones o clases que no existen. Esto último es el fallo más frecuente en lenguajes minoritarios.
  • Lo habitual es que un buen modelo con recuperación de documentación gane al ajuste fino en preguntas de API concretas; conviene probar ambos antes de decidir.

Fase 5. Uso y mejora continua

  • El asistente debe citar la fuente de cada respuesta y decir cuándo no está seguro.
  • Revisar las respuestas dudosas y los fallos, añadirlos como datos corregidos, y reentrenar de vez en cuando.
  • Mantener un registro de la versión de FiveWin y Harbour a la que se refiere cada respuesta.

Riesgos que conviene tener claros

  • Inventar funciones o parámetros que no existen: se mitiga con recuperación de documentación, filtro de compilación y respuestas con fuente.
  • Datos personales y autoría de los posts del foro: anonimizar y revisar la licencia y las normas del foro antes de usarlos para entrenar.
  • Material no público: excluirlo siempre del corpus.
  • Mantenimiento: las versiones cambian, hay que revisar el conjunto de preguntas cada cierto tiempo.

Primer paso pequeño, para probar la idea en un día
Tomar 100 preguntas reales del foro, pedir las respuestas a un modelo con trozos de documentación pública como contexto, y medir cuántas son correctas y cuántas compilan. Si el resultado es bueno, se pasa a las fases 2 a 4 con más datos.
