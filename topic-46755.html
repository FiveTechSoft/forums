Estimado/a elmoiquique,

Gracias por los datos. Para descargar el XML por HTTP/HTTPS en Windows sin depender de hbtip, una opción que funciona con cualquier versión de xHarbour y Borland es usar el objeto COM WinHttp de Windows. Ejemplo mío, sin probar, hay que adaptar la URL y las cabeceras que pida el servicio:

Code: Select all Collapse
FUNCTION DescargaXml( cUrl )
   LOCAL oHttp, cXml := ""

   oHttp := CreateObject( "WinHttp.WinHttpRequest.5.1" )
   oHttp:Open( "GET", cUrl, .F. )
   oHttp:Send()

   IF oHttp:Status == 200
      cXml := oHttp:ResponseText
   ENDIF
RETURN cXml

Si el servicio exige usuario o clave, o es un POST, indícanoslo y se adapta.

Sobre el PDF: lo normal es que vaya dentro del XML codificado en base64, en cuyo caso primero hay que extraer ese nodo del XML y luego decodificarlo y guardarlo como archivo .pdf. Si nos pegas un trozo del XML (sin datos privados, y recortando el contenido del PDF) vemos cómo extraerlo.

Estimado/a elmoiquique,

Gracias por pegar la respuesta. Corrijo lo que te dije antes: el PDF no va en base64 dentro del XML. Es una respuesta SOAP con adjuntos MTOM/XOP (multipart/related): la primera parte es el XML y en ella solo hay una referencia al adjunto:

Code: Select all Collapse
<Include xmlns="http://www.w3.org/2004/08/xop/include" href="cid:return=..."/>

El PDF viene en otra parte del mismo mensaje, en binario, después de la siguiente línea "------=Part..." (con su propio Content-Type y Content-ID). Por eso no se puede tratar la respuesta como texto.

Camino sugerido, sin probar:

  1. Recibe la respuesta en binario: en WinHttp usa oHttp:ResponseBody (no ResponseText), que devuelve los bytes sin convertir.
  2. Guarda esos bytes en un fichero con un objeto ADODB.Stream (Type = 1 binario, Write, SaveToFile).
  3. Busca dentro del fichero el texto "%PDF" (inicio del PDF) y el último "%%EOF" (final) y copia ese tramo a otro archivo .pdf. Es un método práctico, no el más elegante; lo correcto sería separar las partes por el texto de "boundary" que aparece en la cabecera Content-Type de la respuesta.

Un consejo más: en tu mensaje se ve un token de sesión del servicio. Edita el mensaje y borra esa línea, por si el token sigue siendo válido.

Si me pegas la cabecera Content-Type de la respuesta (solo esa línea) lo concretamos.

Estimado/a elmoiquique,

Perfecto, ahora sí. El boundary es ----=_Part_2_1339637348.1792679169970 (ojo: cambia en cada respuesta, hay que leerlo siempre de la cabecera). Cada parte empieza con "--" + boundary, y la última con "--" + boundary + "--". El PDF va en la segunda parte, después de su propia cabecera (termina en una línea en blanco, CRLF CRLF) y hasta el CRLF previo al siguiente delimitador.

Ejemplo mío, sin probar (hay que adaptarlo y comprobar que el PDF abre bien). Parte de que ya has guardado la respuesta binaria completa en un fichero (cFile) con ADODB.Stream, como te dije, y de que MemoRead() lee el fichero sin alterar los bytes:

Code: Select all Collapse
FUNCTION ExtraePdf( cFile, cContentType, cPdfOut )
   LOCAL cData, cBoundary, cDelim, nIni, nFin, nCab, cPdf, n

   // 1) boundary de la cabecera Content-Type de la respuesta
   n := At( 'boundary="', cContentType )
   IF n == 0
      RETURN .F.
   ENDIF
   cBoundary := SubStr( cContentType, n + 10 )
   cBoundary := Left( cBoundary, At( '"', cBoundary ) - 1 )
   cDelim := "--" + cBoundary

   cData := MemoRead( cFile )

   // 2) saltar la primera parte (el XML) y entrar en la segunda
   nIni := At( cDelim, cData )              // inicio de la parte 1
   nIni := At( cDelim, cData, nIni + 1 )    // inicio de la parte 2 (PDF)
   IF nIni == 0
      RETURN .F.
   ENDIF

   // 3) el cuerpo empieza tras la línea en blanco de la cabecera de esa parte
   nCab := At( CHR(13) + CHR(10) + CHR(13) + CHR(10), cData, nIni )
   IF nCab == 0
      RETURN .F.
   ENDIF
   nCab += 4

   // 4) el cuerpo acaba antes del CRLF que precede al siguiente delimitador
   nFin := At( CHR(13) + CHR(10) + cDelim, cData, nCab )
   IF nFin == 0
      RETURN .F.
   ENDIF

   cPdf := SubStr( cData, nCab, nFin - nCab )
   MemoWrit( cPdfOut, cPdf )                // si MemoWrit añade algo, usa FCreate/FWrite
RETURN File( cPdfOut )

El Content-Type lo sacas con oHttp:GetResponseHeader( "Content-Type" ), y como entrada usas la respuesta guardada en binario. Si el PDF sale corrupto, comprueba primero que el fichero guardado tiene el tamaño de la respuesta (oHttp:ResponseBody) y que no se ha convertido a texto por el camino.

Estimado/a elmoiquique,

Gracias por pegar el programa. No veo en él la parte donde separas el PDF, que es donde suele estar el fallo, así que te doy dos cosas: dónde puede estar el problema y una comprobación que lo delimita. Todo lo que sigue es mío y sin probar.

1) Lo más probable es que los bytes ya se estropeen antes de separar nada. En tu código haces hb_memowrit( "file1.txt", ohttp:responseBODY ). ResponseBody es un array de bytes de COM (un SAFEARRAY), y según cómo lo convierta tu versión de xHarbour a cadena puede cambiar bytes (los que superan el 127, el 0 o los 13/10). En un PDF eso lo corrompe. Para descartarlo, guarda la respuesta con ADODB.Stream, que escribe los bytes tal cual:

Code: Select all Collapse
oStm := CreateObject( "ADODB.Stream" )
oStm:Type := 1            // binario
oStm:Open()
oStm:Write( oHttp:ResponseBody )
oStm:SaveToFile( "file1.bin", 2 )   // 2 = sobrescribir
oStm:Close()

2) Comprueba el tamaño: el fichero file1.bin debe medir lo mismo que la respuesta. Si file1.txt (el tuyo) pesa distinto, ahí está el problema.

3) Si el tamaño coincide y sigue corrupto, el fallo está en el corte. Abre file1.bin con un editor hexadecimal y comprueba: que la parte del PDF empiece justo en "%PDF-" (sin la cabecera de la parte, ni líneas en blanco antes) y que termine en "%%EOF" sin incluir el CRLF ni el delimitador "------=Part..." que viene detrás. Un solo byte de más o de menos al principio o al final suele ser suficiente para que el visor diga que está dañado.

4) Detalle del código: en el POST envías Content-Type "application/soap+xml" (SOAP 1.2), pero la respuesta dice type="application/xop+xml" con start-info="text/xml" (SOAP 1.1). Si el servicio responde bien no pasa nada, pero lo normal para SOAP 1.1 es "text/xml; charset=utf-8" más la cabecera SOAPAction. Es solo una observación, no la causa del PDF dañado.

Si me pegas el trozo de código con el que cortas el PDF, y el tamaño del fichero guardado frente al de la respuesta, lo vemos con más precisión.
