What keeps us (still) writing code? And what could this forum be today?

Posted: Tue Nov 24, 2026 08:22 AM

Hello friends,

The forum used to be like a neighborhood pub or coffee shop: drop in briefly, grab a quick coffee, see a few familiar faces, toss a problem across the table, or ask for some advice.

Today, the "Harbour 4" thread has almost 8,000 views and practically no replies. 8,000 readers, a handful of voices. That isn't indifference, but it shows something clear: people are reading, and not enough people are talking.

Especially now, when so much runs through AI tools, you read everywhere that the human element is regaining massive importance—not because of the sheer amount of information, but because of the quality of the exchange. Today, AI often gets things 100% right, yet for our specific situation it often lacks the full context—the context that we have, having accompanied our grown projects and each other for decades. Precisely this shared knowledge and the feeling of making the right choices for the future together is what makes the difference.

With AI, we code differently today: faster and often bolder. Still, the core concepts remain crucial: architecture, clean structures, maintainability, and how to break down tasks so AI can solve them well. At the same time, we face very practical questions about the continuity of our work: how do we successfully market new applications and modernizations? And how do we handle succession or handover for our own projects built over decades? That is exactly what we should be discussing:

Practical AI tips: Which tool, which prompt, and which workflow actually works well with xBase, Harbour, and FiveWin?

Concepts: How do you structure projects so AI can meaningfully assist? What context do you provide?

Pitfalls: Where does AI produce nonsense—for example with legacy xBase code—and how do you catch it?

Tackling legacy systems: Refactoring, documentation, testing. What can finally be accomplished with AI that sat untouched for years?

Future, marketing & succession: How do you position and market new applications to existing or new clients—and how do you cleanly prepare a decades-long life's work for a successor?

One more thought: we are a generation experiencing this transition with full hands-on experience, and we can help shape it. From Clipper and DOS all the way to AI, we have seen it all. That is a tremendous wealth of knowledge that belongs in the conversation—and it is precisely this human experience that connects us.

My suggestion to bring the forum back to life: Let’s start a permanent, shared regulars' thread: "What did I build this week—or what is currently on my mind?" No matter how small the topic is—whether a clever AI workflow, a marketing idea, thoughts on succession, or simply a quick hello from daily development life. A place to drop by without needing a big occasion and feel the value of a genuine community.

How do you see this—and what is keeping you busiest right now? Best regards, Otto

Hi Roberto,

I've had a look at your application, and I think you could migrate it to a web application relatively easily. You have already captured a great deal of domain knowledge in the structure of your DBF files, which should make the transition much easier.

I did a little experiment. As you can see, your original EXE is running, while I access the same DBF files through my microservice and change the name of the warehouse.

What is particularly interesting is that the xBrowse you see in the browser is part of a PHP web application. It accesses the microservice via a domain over the Internet. There is no direct file access from the web application to your DBF files. All data access is handled by the microservice via HTTP/JSON.

Since the microservice is written entirely in Harbour, it uses the same native file and record locking mechanisms as your desktop application.

This means that you could develop individual web modules step by step while your existing desktop application remains fully operational. Both applications could work with the same data in parallel, without requiring a complete rewrite or an immediate migration to another database system.

I think your application is an excellent example of where this hybrid approach could be particularly useful.

Hi Otto,
I know, this example isn't too small.
Below is the full source code that serves for all four anagrafic tables (but actually can manage other types too).

As you can see the source code is primarily a configuration file setting the objects properties and behaviors that are fully managed by the lib,
no forms or reports are designed, no resources except for the bmp's and icons, all the visuals are completely built at runtime by the library objects.
All the tables and views follow the same schema

The module manages the single master data archive (customers, suppliers, agents, carriers) on top of the library's cView framework.
The C_Anagr class configures the view and passes it codeblocks; the real logic lives in the static functions.

  1. New / SetView: work out the master data type (cTipo) from the filter and the calling context (cFrom).
    Based on these, they choose the title, the archives to open, the windows and the value returned in selection mode.

  2. SetBrow: sets up the browse. It adds the function keys that open the related modules on the current record and sets indexes and searches per type. OnIdle refreshes the summary panel above while scrolling.

  3. SetEdit: sets up the edit form: control types, defaults, lookups on related tables and mandatory fields.
    The final check (Controllo) validates the data before saving, for example that at least one master data type is active and that the e-invoicing data is present.

  4. SetLabel: decides which fields are shown and where: the columns in the browse and the three tabs in the form.
    It does this based on the master data type and on compile-time constants.

  5. SetReport: asks for the print parameters and ranges.
    It then prepares one of three layouts (summary with turnover, Excel, standard) and the record filter.

I hope this will be helpful
Roberto

static function Controllo(oEd,lOk)
local cNewKey, cOldKey

if lOk
	begin sequence
		if !(lOk := Ctrl4No(oEd,lOk))
			break
		endif
		
	if oEd:oView:cTipo $ "FCV"			// customers/suppliers/carriers
		if upper(left(oEd:GetBuf("Nazione"),5))=="SELEZ"
			msginfo("Codice stato obbligatorio.")
			lOk := .f.
			break
		endif

		if oEd:oView:cTipo == "C" .and. !oEd:GetBuf("FlagPFis") .and. oEd:GetBuf("IntraCom")=="I" .and.;
			empty(oEd:GetBuf("MailPec")) .and. empty(oEd:GetBuf("CodicePA"))
			msginfo("Attenzione non è stato inserito il Codice univoco né la PEC del cliente. "+;
					"La fattura sarà recapita nel cassetto fiscale del cliente.")
		endif
	endif

end sequence
endif

return (lOk)

static function Ctrl4No(oEd,lOk)
local o, nCtr

// add: check on logical fields - 07/02/2026
load o from nCtr of { oEd:GetFld("FlagCli"), oEd:GetFld("FlagFor"), oEd:GetFld("FlagVet")}
	do case
	case valtype(o:buffer) == "C" .and. o:buffer == "S"
		o:buffer := .t.
	case valtype(o:buffer) == "C" .and. o:buffer == "N"
		o:buffer := .f.
	endcase
next

if lOk
	do case
	case !oEd:GetBuf("FlagCli") .and. !oEd:GetBuf("FlagFor") .and. !oEd:GetBuf("FlagVet")

	lOk := .f.

	#ifdef AGENTI                  // r.c. add: 19/02/2005
		lOk := lOk .or. oEd:GetBuf("FlagAge")		// agents
	#endif

	if !lOk
		Msginfo("Occorre attivare almeno una tabella.;(Cli/For/Age/Vet)")
	endif

case empty(oEd:GetBuf("Categoria"))
	Alert("Codice categoria obbligatorio.")
	lOk := .f.
endcase
endif
return (lOk)
