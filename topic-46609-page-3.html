Me alegra que ya hayas resuelto el punto donde estabas atascado, Rubén.

Para ver qué consultar, separaría dos lecturas:

  • Sintaxis SQL del motor: el README público incluye un apartado SELECT con filtros, ordenación, agrupaciones, agregados, JOIN y otras construcciones documentadas:
    https://github.com/FiveTechSoft/OpenADS
  • Cómo ejecutar y recorrer el resultado desde Harbour: el ejemplo 05_sql.prg que comentamos muestra WHERE con ORDER BY, COUNT/SUM y DISTINCT, y lee el resultado como área de trabajo. No es una referencia exhaustiva del lenguaje:
    https://github.com/FiveTechSoft/OpenADS/blob/main/cookbook/console/05_sql.prg

Son fuentes actuales de la rama main, no una comprobación de que cada construcción esté disponible y funcione igual en tu versión 1.09.74. El ejemplo además crea y borra tablas de prueba: no lo adaptes apuntando a tus datos reales.

Si tienes una consulta concreta que quieras expresar, pega el SELECT deseado y una estructura mínima inventada de las tablas. Así podemos revisar ese caso, en vez de asumir compatibilidad con cualquier sentencia de otro motor SQL.

Rubén, esto es distinto de la consulta que ya conseguiste ejecutar desde Harbour: ahora falla Run en la consola web, aunque la vista de tablas funciona. El mensaje HTTP 500 por sí solo no permite saber qué ocurrió ni demuestra que el JOIN no esté admitido.

He revisado la ruta SQL del servidor en el código público de v1.09.74: el endpoint POST /api/sql ejecuta la consulta y devuelve un cuerpo JSON. Hay una ruta que devuelve 500 si no puede abrir el directorio de datos; en cambio, el error recogido de AdsExecuteSQLDirect se devuelve allí con estado 400 y una descripción. Son rutas distintas, no un diagnóstico de tu caso, y aún no hemos confirmado que el ejecutable del servicio corresponda exactamente a ese código.

La comprobación útil es recoger el detalle que acompaña a ese 500:

  • En las herramientas de desarrollador del navegador, pestaña Red/Network, localiza la petición fallida al pulsar Run y copia solo la ruta, el estado HTTP y su cuerpo de respuesta (Response/Respuesta), si lo tiene.
  • Pega la sentencia SQL que falla, cambiando valores e identificadores privados por otros inventados. Indica si también falla con el mismo SELECT sencillo que ya funcionó desde Harbour, en la copia de pruebas. No hace falta empezar por un JOIN.
  • Si la respuesta no tiene detalle, bastan las líneas del registro del servidor correspondientes a ese intento y la versión que anuncia el servidor al arrancar, si están disponibles.

No publiques cookies, cabeceras de autorización, credenciales, datos devueltos por la consulta ni un archivo HAR completo. Tampoco hace falta reinstalar el servicio, cambiar DLL o abrir puertos para obtener estos datos.
