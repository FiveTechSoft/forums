Carlos, sí: el resultado de una consulta SQL puede quedar en un área de trabajo para recorrerlo o mostrarlo con un browse. En el rddads público de Harbour, AdsCreateSQLStatement crea esa área y la deja seleccionada; AdsExecuteSQLDirect ejecuta sobre ella y, si devuelve un cursor, lo abre en esa misma área. El esquema que buscas no necesita convertir el resultado a un array.

El fallo que muestras ocurre antes de llegar al xbrowse. En el código público de OpenADS v1.09.74, el mensaje «ExecuteSQL: server-side exec failed» lo devuelve el servidor cuando falla su ejecución SQL interna. Ese texto es genérico: por sí solo no identifica el motivo ni demuestra que el SELECT esté mal escrito. Tampoco basta con que la tabla abra por USE para dar por comprobada la ruta SQL.

Para acotarlo sin cambiar DLL ni tocar datos reales:

  • Comprueba primero si AdsCreateSQLStatement devuelve .T. Si devuelve .F., recoge AdsGetLastError inmediatamente y no continúes con ExecuteSQLDirect, para no perder el error de creación.
  • En una copia de pruebas, con una conexión recién abierta, ejecuta el mismo SELECT de rutas como primera operación, antes de abrir tablas o entrar en el browse. Compara también con SELECT * FROM clientes. Basta indicar qué consulta funciona y cuál falla, con el error de cada una; no publiques los registros.
  • Indica el valor exacto que imprime AdsVersion() y la versión que anuncia el ejecutable del servidor al arrancar. No demos por hecho que cliente y servidor corresponden a la misma versión.

Si rutas falla también como primera operación y clientes funciona, el siguiente mínimo útil sería la estructura de rutas y unas pocas filas inventadas que reproduzcan el fallo. Si solo falla después de abrir/cerrar las tablas, la secuencia previa pasa a ser el dato a investigar. Son comprobaciones para separar casos, no un arreglo confirmado; no he reproducido tu entorno.
