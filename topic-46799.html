Philippe,

Do you mean SQL injection through a search/login field, or execution of Harbour code or an external command? These are different risks.

If you mean SQL injection, the MDB password is not a defence against it: once your application has opened the database, the important point is how it builds and executes queries.

A practical first check:

  • Review each place where input is used in SQL, including search filters and imported values. Bind data values as parameters through the database API, rather than joining them into the SQL text. Merely creating a command object is not enough if its SQL was already built by concatenation.

  • For table/column names and sort direction, use fixed choices controlled by the application. Parameters are for values, not arbitrary SQL structure.

  • Test only against a disposable copy with invented data. Start with ordinary values containing an apostrophe, such as O'Brien. Check that the value is handled literally and the query returns only the expected records. A successful test, or the absence of an error, does not prove that every query path is safe.

  • Review the query-building code as well as testing it. Also check separately any path that evaluates expressions or starts external commands; parameterized SQL does not protect those paths.

Which access layer do you use for the MDB: ADO, ODBC, or something else? Please post one small example showing how a query is built and executed, with dummy field names and values. Do not include the MDB password, connection secrets or real records. With that we can check the actual path instead of guessing at an API-specific example.

I wonder whether SQL injection was underestimated by some Harbour programmers when they moved from DBF to MDB or SQL.

A typical part of that transition may be carrying over the DBF way of thinking: “I’ll build a search expression.” With DBF, dynamically assembling search conditions was familiar. With SELECT, it can seem just as straightforward. But the expression is now interpreted by a SQL engine. If user input is inserted directly into the SQL text, it can change the query.

SQLRDD supports commands such as SELECT, INSERT, UPDATE and DELETE, so SQL statements are executed at runtime. SELECT is practical, but when a query is assembled as text, it is not always obvious where the query ends and the input begins. That calls for a different mindset: bind values instead of inserting them into the SQL text.

Perhaps the effort involved in operating a SQL Server was underestimated too. It requires appropriate user permissions, secure network settings, regular updates and reliable backups whose restoration is tested. A SQL Server does not provide this security automatically. If it is poorly maintained, it can introduce additional risks instead of making the application more secure.
