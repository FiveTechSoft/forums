Estimado Leandro:

Gracias por compartir la traza y el código. El error concreto no apunta por sí solo a xHarbour de 64 bits. En TControl:_nHeight, el operador + recibe un bloque (B) y el número 391. En tu ejemplo, SetCoors() recibe las cuatro coordenadas como bloques { | o | ... }. TDockPnel:SetCoors() calcula una altura numérica, pero conserva nTop como bloque; al asignar nHeight, el setter de TControl intenta sumar ese nTop al número y falla.

Para aislarlo, prueba primero con coordenadas numéricas para ambos paneles, sin cambiar el resto de tu código:

Code: Select all Collapse
oDock1:SetCoors( 10, 10, 390, 390 )
oDock2:SetCoors( 10, 400, 390, 780 )

Son valores de prueba (nTop, nLeft, nBottom, nRight), no tamaños definitivos de tu ventana. Si así desaparece el BASE/1081, calcula esas cuatro coordenadas como números antes de llamar a SetCoors(). Para conservar el ajuste al redimensionar, habría que volver a calcularlas al cambiar el tamaño de la ventana; no dejes un bloque almacenado en nTop en esta ruta.

También veo una discrepancia útil para reproducirlo: el título dice FWH 26.06, pero el log informa FWH 26.03. ¿Cuál de las dos versiones genera exactamente esa traza? Si tras cambiar las coordenadas sigue fallando, comparte la traza nueva y podemos seguir desde el siguiente punto.
