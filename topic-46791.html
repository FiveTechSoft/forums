Hi Byron,

This is consistent with the linker not extracting the object that contains your INIT PROCEDURE from the library. Listing the .LIB does not necessarily pull in every object it contains.

You can give that object a public anchor and REQUEST it from the application.

In the SAME .PRG that contains SetUpClass() and your static methods, add this at file scope, outside the INIT PROCEDURE:

Code: Select all Collapse
FUNCTION McsPrinterExtLink()
RETURN NIL

Rebuild your library. Then add this at file scope in your application's main .PRG:

Code: Select all Collapse
REQUEST McsPrinterExtLink

Keep your library in the link list. The REQUEST creates the reference that brings in that library member, including its INIT PROCEDURE. You do not need to call the anchor or SetUpClass() yourself, and your method implementations can remain STATIC.

The anchor must be in the same library member as the initialization code. If extensions are split across separate .PRG/object files, use a separate anchor for each required member.

I checked a minimal static-library example with EXTEND CLASS, an INIT PROCEDURE and a STATIC method: without REQUEST the extension was absent; with REQUEST the INIT ran and the added method returned the expected value. That test used Harbour win64, FWH 26.10 and LLVM-MinGW under Wine, not Borland C++ 7.0 or xHarbour. It supports this approach, but does not prove the cause in your particular library.

If it still does not work, please post your Harbour/xHarbour version and the actual linker command or response file, with private paths removed.

REQUEST reference:
https://www.hamor.ro/distr_ext/Doc/xHb/xHarbour%20Language%20Reference/Statements/Request.en.html
