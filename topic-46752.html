Estimado/a remtec,

En una aplicación FiveWin (GUI) un bucle DO WHILE .T. sin más bloquea la cola de mensajes de Windows, y Inkey() solo lee el teclado de consola, así que no suele ver la tecla ESC. Hay dos formas habituales:

1) La más limpia: no usar un bucle, sino un TTimer que se dispare cada pocos segundos, haga la consulta a la base de datos e imprima, y se desactive con ESC (por ejemplo desde el bValid o el bKeyDown del diálogo/ventana, llamando a oTimer:Deactivate()).

2) Si prefieres mantener el bucle, llama a SysRefresh() dentro de él (para que Windows procese mensajes) y consulta la tecla con GetAsyncKey( VK_ESCAPE ), que existe en FiveWin (winapi/keybrd.c) y devuelve .T. si está pulsada:

Code: Select all Collapse
DO WHILE .T.
   SysRefresh()
   IF GetAsyncKey( VK_ESCAPE )
      EXIT
   ENDIF

   // aquí abres la base de datos, compruebas el último registro
   // e imprimes si hace falta

   SysWait( 1 )   // espera 1 segundo procesando mensajes, para no saturar la CPU
ENDDO

Ojo: este código es un ejemplo mío y no lo he probado. Ten en cuenta que GetAsyncKey detecta la tecla ESC aunque otra aplicación tenga el foco, por eso la opción del TTimer es más segura si el usuario trabaja con otros programas a la vez.

Estimado/a remtec,

Corrijo mi ejemplo anterior: el timer debe crearse dentro del ON INIT del diálogo, cuando la ventana ya existe. Definido antes, queda ligado a una ventana inexistente y no llegaría a dispararse. Esta es la versión correcta, con el mismo patrón que usan los ejemplos de la propia FiveWin:

Code: Select all Collapse
#include "fivewin.ch"

STATIC oTimer

FUNCTION ImpresionContinua()
   LOCAL oDlg

   DEFINE DIALOG oDlg FROM 0, 0 TO 120, 400 PIXEL ;
      TITLE "Revisión de impresiones (pulse ESC para terminar)"

   ACTIVATE DIALOG oDlg CENTERED ;
      ON INIT IniciaTimer( oDlg ) ;
      VALID ( oTimer:End(), .T. )   // al cerrar (ESC o el aspa) paramos el timer y salimos

RETURN NIL

STATIC FUNCTION IniciaTimer( oDlg )

   // El diálogo ya existe: el timer queda ligado a su ventana
   DEFINE TIMER oTimer OF oDlg INTERVAL 3000 ACTION RevisaEImprime()

   ACTIVATE TIMER oTimer

RETURN NIL

STATIC FUNCTION RevisaEImprime()

   oTimer:Deactivate()   // evita que el timer vuelva a dispararse mientras trabaja

   BEGIN SEQUENCE

  // Abrir la base de datos
  // Comprobar si el último registro ingresado ya está impreso
  // Si no lo está, imprimirlo
  // Cerrar la base de datos

   RECOVER

  // Si algo falla a mitad, seguimos para reactivar el timer

   END SEQUENCE

   oTimer:Activate()

RETURN NIL

Cómo funciona:

  • TTimer guarda la ventana del propietario en el momento de crearse; por eso se define en ON INIT, cuando el diálogo ya existe (es el patrón de los ejemplos gettime.prg y meter01.prg de FiveWin).
  • Ya no hay bucle: el timer dispara RevisaEImprime() cada INTERVAL milisegundos (3000 = 3 segundos; ajústalo a tu caso).
  • ESC cierra el diálogo (comportamiento estándar de TDialog en FiveWin) y el VALID ejecuta oTimer:End(), que detiene el timer y lo libera antes de salir, así no queda nada ejecutándose en segundo plano.
  • El Deactivate/Activate evita que el timer se dispare de nuevo si una pasada tarda más que el intervalo, y el BEGIN SEQUENCE/RECOVER hace que el timer se reactive aunque la rutina falle a mitad.
  • Si tu programa ya tiene una ventana abierta, puedes definir el timer con OF oWnd sobre esa ventana en lugar de crear el diálogo.

Este código sigue siendo un ejemplo mío que no he compilado ni ejecutado, aunque ahora está contrastado con el código fuente y los ejemplos de FiveWin; adáptalo a los nombres de tu base de datos y tu rutina de impresión.

Una precisión sobre ese enfoque, verificada en el fuente de FiveWin: SysRefresh() procesa un mensaje pendiente de Windows por llamada (de cualquier tipo, no solo teclas; hace PeekMessage + TranslateMessage + DispatchMessage en winexece.c). El problema del bucle DO WHILE no es que la aplicación deje de atender mensajes, sino que el hilo principal queda girando sin parar dentro del bucle: hasta que no se pulse ESC, el resto de la lógica del programa no avanza, y ese sondeo continuo mantiene un núcleo de CPU ocupado todo el rato. Es una explicación plausible del "cuelgue" que describes, aunque no puedo confirmar que sea la causa exacta en tu equipo sin ver el código completo del bucle.



Para tu caso, esperar a que se grabe un vale nuevo para imprimirlo, el enfoque del timer encaja mejor: el diálogo sigue activo con normalidad y Windows llama al bloque del timer cada X milisegundos, sin sondeo continuo. Ahí puedes comprobar la base y lanzar la impresión cuando aparezca el vale.



Te remito al ejemplo corregido de mi mensaje anterior en este hilo: el timer se crea dentro de ON INIT (crearlo antes de ACTIVATE DIALOG hace que nunca se dispare, porque aún no existe la ventana) y con reactivación tras un error. Estimado/a remtec,

El síntoma que describes (la ventana se muestra, pero el ACTION no se ejecuta) es coherente con un defecto localizado y verificado en el fuente de FiveWin: en tu código el DEFINE TIMER se ejecuta ANTES del ACTIVATE DIALOG. Al crearse, TTimer guarda el handle de la ventana del diálogo (::hWndOwner := oWnd:hWnd, en timer.prg), pero antes del ACTIVATE la ventana todavía no existe y ese handle vale 0. FiveWin despacha los timers a través del procedimiento de la ventana dueña (TWindow:Timer, que llama a TimerEvent en timer.prg), y con handle 0 no hay ventana dueña válida para ese despacho: según el comportamiento documentado de Win32, un WM_TIMER sin ventana queda en la cola del hilo sin destinatario al que entregarlo. Así que el mecanismo verificado en fuente explica que Buscava() no llegue a ejecutarse; la confirmación definitiva la dará tu prueba con la corrección aplicada.

La corrección: crear el timer DENTRO del ON INIT, cuando el diálogo ya existe. No basta con activarlo ahí; hay que crearlo ahí. Es el cambio que apliqué al ejemplo corregido de mi mensaje anterior. Aplicado a tu código:

Code: Select all Collapse
STATIC oTimer

FUNCTION Imp_vale_aut()

   LOCAL oSay, oDlgoBtn1, oDlg2
   LOCAL oFont, oFont1, oFont2, oFont3

   Private Ing_xbro := 0, oPrn, oRigen := 1
   Public oIngre, Mensa := "", nIni := 0, nFin := 0, oIni, oFin

   // ... tu inicializacion igual (HB_LangSelect, SET DATE, rddRegister, etc.) ...

   DEFINE DIALOG oDlg2 FROM 0, 0 TO 120, 400 PIXEL ;
      TITLE "Imprime Vales de Caja Automatico, (Pulse ESC para Salir)."

   ACTIVATE DIALOG oDlg2 CENTERED ;
      ON INIT IniciaTimer( oDlg2 ) ;
      VALID ( oTimer:End(), .T. )

RETURN NIL

STATIC FUNCTION IniciaTimer( oDlg )

   // Aqui el dialogo ya existe: el timer queda ligado a su ventana
   DEFINE TIMER oTimer OF oDlg INTERVAL 9000 ACTION Buscava()

   ACTIVATE TIMER oTimer

RETURN NIL

Y un detalle más en Buscava(): escribiste oTimer:Desactivate(), pero el método se llama DeActivate() (sin la "s"; verificado en timer.prg). Con la "s" daría un error de ejecución al entrar en la rutina. Recuerda también reactivar el timer al salir de Buscava() con oTimer:Activate(), para que el ciclo continúe, idealmente protegiendo el trabajo con BEGIN SEQUENCE / RECOVER como en el ejemplo anterior.

Como siempre: código verificado contra el fuente de FiveWin, no ejecutado aquí en Windows.
