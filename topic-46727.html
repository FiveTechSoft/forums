Estimado FiveWiDi:

Gracias por la consulta y por el detalle con que la describes. Lo que sigue son tres cosas: qué hemos comprobado, cómo funciona el disparo de bChange y una hipótesis a verificar en tu código.

1. ¿Ha cambiado TListBox o la ejecución de eventos?

Hemos revisado el historial de la rama principal de FWH. listbox.prg no ha tenido commits en los últimos 12 meses aproximadamente. Los más cercanos, de marzo de 2026, son una protección contra NIL en LButtonDown, unas guardas en Reset/LostFocus y un cambio de formato. Ninguno toca TListBox:Change(). Tampoco hemos visto cambios recientes en control.prg ni window.prg (HandleEvent, KeyDown, Command) que alteren la cadencia con la que se dispara bChange. Por tanto, no hay nada reciente en la clase que explique por sí mismo un comportamiento nuevo.

2. Cómo se dispara bChange

TListBox:Change() hace esto, en este orden:

Code: Select all Collapse
- si hay items y bSetGet es un bloque:
    - evalúa bSetGet con el índice (1-based) o con el elemento, según LB_GETCURSEL
    - evalúa bChange( Self )

La llamada a bChange es síncrona y no hay SysRefresh() entre medias. No hemos localizado en este análisis la ruta exacta por la que Windows llega hasta Change() con las flechas, así que no afirmamos nada sobre eso.

3. Hipótesis (sin afirmar causa)

Con las flechas pulsadas rápido, los cambios de selección se encadenan y cada uno ejecuta tu función. Dos cosas a revisar dentro de ella:

  • Posicionamiento del registro. Si lees con oTDbf:Load() y compruebas si está borrado, asegúrate de que el DBF está posicionado en el registro que corresponde al item seleccionado, y no en el que quedó de la llamada anterior. Por ejemplo, guardando el número de registro de cada item y haciendo el GoTo antes de Load() y de la comprobación de borrado:
Code: Select all Collapse
function CambioRec( oLbx, oTDbf, aRecnos )

   local nRec := aRecnos[ oLbx:GetPos() ]   // registro del item seleccionado

   oTDbf:GoTo( nRec )                       // posicionar siempre antes de leer
   oTDbf:Load()

   if oTDbf:Deleted()
      return nil                            // no se actualiza
   endif

   // ... actualizar campos ...

return nil

Es un esquema orientativo: los nombres de los métodos de TDBF y de la lista de registros dependen de tu código.

  • SysRefresh() dentro de bChange. Procesa mensajes pendientes, así que puede atender más pulsaciones de flecha y volver a entrar en tu función antes de terminar la anterior. Si el registro cambia a mitad de ejecución, la comprobación de borrado puede hacerse sobre otro registro. Prueba a quitarlo de ahí.

TDBF es una clase de terceros (Manu Expósito), y no podemos garantizar nada sobre su comportamiento interno.

Si el problema persiste, un ejemplo mínimo que lo reproduzca (un listbox, unos pocos registros, uno borrado y la función bChange) permitiría ver con datos qué ocurre.

   REDEFINE LISTBOX oLbx VAR nItem ITEMS aItens ID 101 OF oDlg ;

RETURN NIL

   ENDIF

RETURN AllTrim( cValToChar( oDbf:FieldGet( cCampo ) ) )

Estimado karinha:

Gracias por el ejemplo, es justo el patrón de bChange con TListBox del que hablábamos en este hilo.

Un detalle en la llamada a DbLbxChange() dentro de bChange: le pasas 6 argumentos, pero la función está declarada con 5 parámetros. Harbour no da error, simplemente ignora el sobrante, y por eso los SAY quedan desplazados:

Code: Select all Collapse
// Tu bChange (6 argumentos):
oLbx:bChange := { || DbLbxChange( oLbx:GetPos(), oDbf, aRecnos, ;
                                  oSay1, oSay2, oSay3 ) }

// Tu función (5 parámetros):
STATIC FUNCTION DbLbxChange( nPos, oDbf, aRecnos, oSay2, oSay3 )

Dentro de la función, oSay2 recibe en realidad oSay1 (el texto "Nombres:") y oSay3 recibe oSay2. Por eso, al cambiar de fila, el texto "Nombres:" se sustituye por el registro, el segundo SAY muestra la dirección y el tercero no cambia nunca. En ON INIT sí funciona bien, porque ahí pasas solo dos SAY.

La corrección es pasar los mismos dos SAY que en ON INIT:

Code: Select all Collapse
oLbx:bChange := { || DbLbxChange( oLbx:GetPos(), oDbf, aRecnos, ;
                                  oSay2, oSay3 ) }
