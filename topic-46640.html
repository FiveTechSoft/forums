Printer class problem

Posted: Fri Jul 24, 2026 08:09 PM

I'm using FWH 25.091 and xHarbour and I'm using the tprinter class to print some simple reports. Reports that have worked for years, stopped working when I upgraded to FWH 25.09.

The entire app closes without any error messages or log after processing a random number of records. For example, I have a simple customer report that does a loop printing one page per customer and it may process one, several dozen, or hundreds of customer records before the app just closes before reaching the print preview. Everyone once in a while it finishes with the print preview.

I have added some logfile calls and when it fails it always does so at this line in printer.prg source.

::hDCOut := CreateEnhMetaFile( ::hDC, ATail( ::aMeta ), ::cDocument ) //jlcr

I have monitored the GDI objects in the task manager and they do not grow, just increment/decrement by one for each page. when I look in the user temp folder there are emf files for all the pages however, the last emf file is empty, size is 0 bytes.

Any idea why this is happening?

Thanks, Randal

Dear Randal,

Root Cause Analysis
The crash originates from CreateEnhMetaFileW failing inside metafi32.c (line 30-34). Here's the critical chain of events:
What happens in the C wrapper (source\winapi\metafi32.c):
pFile = fw_parWide( 2 ); // temp file path (UTF-16)
pDesc = fw_parWide( 3 ); // document name (UTF-16)
hdcRet = CreateEnhMetaFileW( (HDC) hb_parnl(1), pFile, &rect, pDesc );
When CreateEnhMetaFileW fails, it returns NULL. The C code does show a MessageBoxW — but the caption of that MessageBox is the raw temp file path (the full temp directory path), and the body says something like "Error (8) creating enhanced metafile". You may simply not be noticing this dialog — it's easily missed when the app appears to "just close."
The 0-byte EMF file confirms the sequence: CreateEnhMetaFileW creates the file on disk first, then returns. If it returns NULL, the file stays at 0 bytes because CloseEnhMetaFile is never called (which would write the actual metafile data).
Why it fails after a random number of pages
The most likely cause is file handle exhaustion. Here's why:

  1. Each page in _StartPage() (line 621-622) creates a new EMF file via CreateEnhMetaFile
  2. Each page in _EndPage() (line 653) calls CloseEnhMetaFile which should close the file handle
  3. But xHarbour has a default file handle limit (typically 256). If your application also has database files open (USE, DBUSEAREA, etc.), ODBC connections, or other file operations, the available handles get consumed
  4. After a random number of pages, CreateEnhMetaFileW can no longer open a new file → returns NULL
    The "random" count is because the number of simultaneously open handles varies depending on which records trigger which code paths.
    The secondary crash
    Once CreateEnhMetaFile returns NULL, ::hDCOut becomes 0. Then subsequent drawing operations (like Line, Say, FillRect, etc.) call Windows GDI functions with an invalid HDC (0), which causes an access violation that terminates the process — this is why you see no further log output.
    The check if ::hDCOut = 0 / return nil exists in some methods like _FillRect (line 1420), but not in all drawing methods. For example, Line() (line 690) does:
    MoveTo( ::hDCOut, nLeft, nTop )
    LineTo( ::hDCOut, nRight, nBottom, ... )
    No NULL check — instant crash.
    Recommended Solutions
  5. Increase xHarbour file handle limit (Immediate fix)
    At the start of your application, before creating the printer:
    SET FILEHANDLES TO 512 // or higher, e.g. 1024
    This is the most likely fix. xHarbour defaults to a low number, and each EMF page + any open DBFs consume handles.
  6. Check if the MessageBox IS appearing
    Temporarily add this before your StartPage() call to confirm:
    msginfo("About to start page " + str(nPage + 1))
    oPrinter:StartPage()
    If you see the MessageBox flash or appear behind windows, that confirms CreateEnhMetaFile is failing. The MessageBox caption will be the full temp path.
  7. Add defensive code (Workaround in user code)
    Wrap your print loop to catch the failure:
    oPrinter:StartPage()

if oPrinter:hDCOut == 0
msgstop("Failed to create metafile page. Check file handles.")
oPrinter:EndPage() // cleanup
exit
endif

// ... your drawing code ...

oPrinter:EndPage()

  1. Reduce open file handles during printing
    Make sure you're not holding unnecessary files open during the print loop:
  2. Close any USEd database files that aren't needed during printing
  3. Close any file handles opened with fopen() / fcreate() before the loop
  4. If using ODBC, ensure connections aren't keeping cursors open
  5. Verify TEMP path accessibility
    msginfo("Temp dir: " + getenv("TEMP"))
    msginfo("Free space: " + str.diskfree(getenv("TEMP")))
    Ensure the temp directory exists, is writable, and has sufficient space.
    Quick diagnostic test
    Try this minimal test to isolate the issue:
    Code: Select all Collapse
    local oPrinter, n
oPrinter := TPrinter():New("Test", .f., .t.)  // lPreview = .t. forces meta mode

for n := 1 to 500
   oPrinter:StartPage()
   

   if oPrinter:hDCOut == 0
      msgstop("Failed at page " + str(n))
      exit
   endif
   

   oPrinter:Say(1, 1, "Page " + str(n))
   oPrinter:EndPage()
next

oPrinter:Preview()
    If this fails at a certain page number, that's your file handle limit. Increase SET FILEHANDLES TO accordingly.
    TL;DR: The most probable cause is xHarbour's file handle limit being too low for the number of EMF pages your report generates. Add SET FILEHANDLES TO 1024 near the start of your application and test again.
