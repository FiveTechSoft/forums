The Rebirth of DBF? – A New Perspective on Cybersecurity

Posted: Sun Nov 08, 2026 01:39 AM

Dear friends,

For decades, we have discussed DBF versus SQL, usually focusing on performance, scalability, and modern technology.

But perhaps today's completely different cybersecurity threat landscape gives us a reason to reconsider DBF.

Two questions seem particularly important to me:

  1. How can we protect our applications and customer data from cyberattacks?

  2. How quickly and reliably can we recover our original data after a successful attack?

Let's compare DBF and SQL under the same security conditions: no SMB shares, no direct database access from workstations, and all communication through a secured microservice.

With DBF, a Harbour microservice accesses local DBF/FPT files directly.

With SQL, we introduce an additional, continuously running database server that needs its own configuration, updates, monitoring, and protection.
And there is another important distinction: Knowing how to write SQL queries and knowing how to securely install, configure, maintain, and recover a SQL server are two completely different skills.

Being a good SQL programmer does not automatically make someone a qualified database administrator.
Does this additional service also create an additional attack surface?

Of course, DBF is not automatically secure. The operating system, microservice, access permissions, and backups must all be properly protected.

But DBF also has an interesting advantage: our original data remains in directly accessible files, potentially simplifying recovery, provided we have consistent and protected backups.

Perhaps we should reconsider DBF, not out of nostalgia, but from the perspective of today's security requirements.

I would be interested in your practical experiences with server security, microservices, offline backups, and disaster recovery.

Could today's cybersecurity challenges actually lead to a rebirth of DBF?

Otto, separating prevention from recovery is a useful way to frame this. I would judge the complete deployment and its recovery procedure, rather than declare either storage format the safer choice.

In the architecture you describe, removing workstation access to the data and putting access checks in a service is an important boundary. The next question is what happens if that service, or its account, is compromised. Which records can it read or change? Can it also delete the backups? These questions matter with either backend.

An additional database service is another component to configure, patch and monitor, yes. But that does not necessarily mean another publicly reachable endpoint: OWASP recommends restricting database access to the required hosts, or using local-only access where appropriate. Counting services alone does not establish the overall risk. Equally, a local DBF directory should not be treated as protected merely because it has no SMB share.

For recovery, I would compare a concrete restore exercise:

  • What is the maximum acceptable data loss, and how long can the business remain offline?
  • How is a consistent backup produced while the application is writing? For DBF, does the procedure cover the related memo files and the chosen index recovery/rebuild procedure?
  • Can the production account alter or erase every backup, or is there a protected offline copy?
  • Can the application and its configuration be rebuilt on a clean machine, and has someone actually restored the data and checked the business results there?

CISA recommends offline, encrypted backups and regular restoration testing. It also stresses that ransomware can involve data theft: restoring the files addresses availability, but does not undo disclosure.

So yes, DBF deserves consideration when it fits the application and the team can operate and recover it reliably. I would not turn that into a general security advantage over SQL without evidence from comparable deployments. A documented, timed restore test would make this discussion much more useful than a format-only comparison.

References:
https://www.cisa.gov/stopransomware/ransomware-guide
https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html

Again, during the application planning stage, ( best practice ) in the Corporate world is to discuss if the CIO prefers a SQL server or something portable as MS Access or .dbf data tables. We as programmers need to be flexible enough to include the CIO's corporate BEST defenses against a cyber attack and plan our database backend around the Best preference of the Corporate CIO.

I really do not think there is any ( real ) perfect answer here and the use of any database should be discussed with Mom and Pop and or the Corporate CIO and plan accordingly at best the Deterrence to include daily backup of any data type the Customer or Corporate CIO prefers, since Security is the responsibility of the Customer or Corporate entity.

Hi Rick,

I agree with you that the final decision about data security belongs to the CIO.

For me, as the CIO of my own company, one of the biggest challenges today is how to store sensitive information securely on our own computers while still being able to access it remotely through a web interface, from anywhere.

This is not necessarily a question of DBF versus SQL. Both have their advantages, but neither automatically protects us if an attacker gains sufficient control over the server.

That is why we developed WinHotel AIRBAG, a small security tool based on Windows BitLocker.
Our current focus is mainly on document management – contracts, confidential documents, password vault files and other sensitive information.

The idea is quite simple:
Documents are stored in their original formats on a separate BitLocker-encrypted drive.
The drive remains locked, even while Windows is running.
An authorized user can unlock it through a simple web interface by entering the BitLocker password.
After accessing or saving documents, the drive can be locked again.
The BitLocker password is never permanently stored by AIRBAG.
We use Windows' built-in encryption instead of developing our own.

Unlocking the drive currently takes about five seconds. We are aware of this delay, but for us, the simplicity and additional security are well worth it.

We are also considering an independent Windows task that automatically locks the drive again after a short period. Even if our application crashes or is terminated, this separate task could still attempt to lock the drive.

Another important consideration is recovery.

Our documents remain ordinary PDFs, images and other files. With a valid backup and the BitLocker recovery key, we can access them on another Windows computer without needing to restore a SQL Server or even our own application.

Of course, there are limitations. A fully compromised Windows administrator could potentially access files while the drive is unlocked or interfere with the locking mechanism. We cannot eliminate every risk.

But we can significantly reduce the time during which sensitive information is accessible.

And that is really the point of AIRBAG:

Why should confidential documents remain accessible 24 hours a day when we only need them for a few seconds or minutes?

AIRBAG is not intended to replace SQL or DBF databases. It is an additional layer of protection for sensitive information, using technology already available in Windows.

For our company, this combination of simplicity, security and straightforward recovery is very convincing.
