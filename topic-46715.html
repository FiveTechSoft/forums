Estimado Carlos:

Gracias por tu reporte tan detallado, con código y capturas. Hemos revisado el código fuente actual de TGet y creemos haber encontrado la causa.

Al activarse el diálogo, TGet:Initiate() detecta el estilo ES_PASSWORD del control del .RC y marca el GET como tipo password. A continuación se ejecuta TGet:DispText(), que es quien escribe el texto en el control. En esa función existe una rama específica para los GET password: si el control todavía está vacío (y al crearse desde un recurso .RC siempre lo está, porque EDITTEXT no admite texto inicial), se reescribe en el control su propio contenido, es decir, nada. El valor que ya tenía la variable no llega al control en ese momento.

El valor solo se escribe cuando el GET recibe el foco, desde TGet:GotFocus() -> SetTextSize(), que evalúa la variable y hace SetText() con su contenido. En ese instante Windows lo muestra enmascarado (los puntos que ves). Por eso el GET de usuario aparece relleno desde el principio y el de clave solo al enfocarlo: en los GET normales DispText() sí escribe el contenido del buffer desde el inicio.

No es un error de tu código ni del PICTURE "@": es el comportamiento actual del framework en este caso concreto (GET redefinido desde recurso con ES_PASSWORD y valor prefijado).

Mientras tanto, puedes escribir el valor en el control desde el ON INIT del diálogo, que se ejecuta cuando los controles ya están iniciados:

Code: Select all Collapse
ACTIVATE DIALOG oDlg ON INIT oUserPass:SetText( cUserPass )

Así el control recibe el texto al crearse el diálogo y se muestra enmascarado desde el primer momento.
