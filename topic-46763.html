Dear Enrico,



These LNK2001 messages concern five Harbour compatibility functions used by TWebView2: hb_DirSepAdd(), hb_DirSepToOS(), hb_defaultValue(), hb_DirBuild() and hb_HHasKey(). The linker is not resolving them in your xHarbour build. This happens before the program runs, so it is not a WebView2 navigation or panel-positioning error.



I checked the current FWH source: the xHarbour compatibility implementations are in harbour.prg, and the library build includes that module together with twebview2.prg. The current xHarbour/MSVC32 build uses Fivehx32.lib. However, the name fivexm32.lib in your output alone does not tell us which FWH version or library build you have, and I have not reproduced your MSVC link.



Could you please post your exact FWH version/build and the complete linker command (or the library list from your .mak/.bat), including the paths used for the FWH and xHarbour libraries? This will let us check which library is actually being selected and whether the compatibility module is available to that link, rather than changing your sample blindly.

Dear Antonio,

Yes, reducing TWebView2's dependence on Harbour-specific helper functions is a sensible direction. I checked the current source: the class calls these helpers directly, while harbour.prg supplies compatibility implementations under __XHARBOUR__.

The replacement needs to preserve behaviour, not just use a different function name: hb_defaultValue() checks value types, hb_DirBuild() creates nested folders, hb_DirSepAdd() preserves the drive-relative C: case, and hb_HHasKey() checks whether a hash contains a key. Directory handling must also preserve UNC paths and unavailable-root handling.

So the compatibility layer already exists, but a replacement based on APIs common to both compilers still needs to be checked and tested with Harbour and xHarbour. I have not validated such a replacement or reproduced Enrico's MSVC link, so I cannot yet present it as a confirmed fix. His exact build and library paths would still help distinguish an unresolved compatibility-module link from the proposed source-level change.
