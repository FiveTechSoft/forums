Attachment fails to download at recipient (Simple MAPI) — regression between FWH 26.03 and 26.09

Posted: Tue Sep 22, 2026 10:54 PM

We're seeing a reproducible regression in DEFINE MAIL / MAPISendMail() attachment delivery between FWH 26.03 and the current 26.08 build. Same machine, same Outlook profile, same Exchange Online mailbox, same recipient, same file — only the linked FWH library version changes.

Code (unchanged across all tests): harbour LOCAL oMail, lSent

DEFINE MAIL oMail ; SUBJECT cSubj ; TEXT cText ; FILES cSndFile, cSndFile ; FROM USER ; TO MailTo, MailTo

SEND MAIL oMail

lSent := ( oMail:nRetCode == 0 ) // returns 0 (success) in every version tested

Symptom: MAPISendMail() returns SUCCESS_SUCCESS (0) in all versions — the send appears to succeed locally, and Outlook's own Sent Items shows it as sent. But on the recipient side (Outlook, both Windows and Mac clients, mailbox hosted on Exchange Online), the attachment shows as not downloaded, with a "try again later" prompt that never resolves on retry. No attachment ever becomes available to the recipient.

Versions tested (same source, same test, only FWDIR changed):

┌─────────────────────────────────────────┬────────────────────────────────────────────────────┐ │ FWH version │ Result │ ├─────────────────────────────────────────┼────────────────────────────────────────────────────┤ │ FWH 25.12 (fwh642512) │ Works — attachment delivers and opens normally │ ├─────────────────────────────────────────┼────────────────────────────────────────────────────┤ │ FWH 26.03 (fwh642603) │ Works — attachment delivers and opens normally │ ├─────────────────────────────────────────┼────────────────────────────────────────────────────┤ │ FWH 26.08 (current, freshly downloaded) │ Fails — attachment stuck undeliverable, every time │ └─────────────────────────────────────────┴────────────────────────────────────────────────────┘

What we've ruled out on our end before posting: we diffed mail.ch, tmail.prg, and mapi.c line-by-line between 26.03 and 26.08 — the only changes in mapi.c are the new MapiFillAddressIfEmpty() recipient-address fallback and some GetProcAddress cast cleanups; nothing touches MapiFileDesc/lpszPathName/lpszFileName. We also extracted the compiled mapi.obj from both fivehc64.lib versions directly and confirmed the binary matches that source diff — so whatever changed isn't in the mail-handling source itself. We also confirmed our own application code and the exact TO/FILES call are identical across both builds.

Given the mail-specific source is unchanged, is there anything elsewhere in the 26.09 build (a linked dependency, manifest, or process-wide initialization change) that could affect how Simple MAPI attachments are staged/delivered through Exchange Online — even though MAPISendMail() itself reports success? Happy to provide a Process Monitor trace comparing both builds if that would help narrow it down.

Dear Tim,

Short answer: nothing I can find in the 26.03→26.08/26.09 delta plausibly explains this — and your source-level diligence is correct. Details:
Mail stack is functionally unchanged
tmail.prg and mail.ch have zero diff since 26.03. The only semantic change in mapi.c is MapiFillAddressIfEmpty() (26.07, commit 29a55fab7), which is a no-op for your TO MailTo, MailTo form (address is already non-empty). GetProcAddress casts, static keyword order, and an xhbcompat.h include (no-op on Harbour builds) are the rest. Your mapi.obj binary comparison matches.
Non-mail candidates I checked — all weak
Candidate Verdict
fwunicode.c hbcdp_to_wincdp() now skips OEM codepages (26.06) Not on this path — mapi.c passes raw hb_parvc() pointers, no FWH codepage conversion
Dark mode expanded to TWindow (2026-08-19) Only if app calls FW_SetDarkMode(.T.)
files.c share-mode/_sopen changes None — only warning cleanups / SHA256 define
Process CWD / lChDir in TMail:Activate() Unchanged since 2018
Manifest / comctl32 v6 Lives in the app's .rc, not the FWH libs — same EXE resource either way
xHarbour compat layer (hb_parvc shims) Only if you link xHarbour variants — you're on FiveHC64 (Harbour+MSVC64), so no-op
FIVEWIN.CH static decls moved / TRY-CATCH map Preprocessor only, doesn't touch DEFINE MAIL
Nothing in 26.09 initializes a process-wide hook, MAPI wrapper, or file-staging path that could alter MapiFileDesc delivery.
What the symptom actually implies
MAPISendMail()==0 + Sent Items shows sent + recipient sees an undownloadable attachment means the message was submitted with bad attachment content/metadata, not that FWH "failed to attach." Since FWH only passes lpszPathName (a pointer into your Harbour string) and lets Outlook/mapi32 read the file, the realistic failure modes are:

  1. Outlook read different bytes / partial file at send time (lock, OneDrive placeholder, cloud-attachment path), or
  2. Something post-submission — but that can't correlate with FWDIR unless the submitted bytes differ.
    Critical bisect you can do without ProcMon: open the sent message in Sent Items on the sender side in each version and check the attachment there (size, openable?).
  3. Broken in Sent Items too → client-side staging confirmed → ProcMon will show it
  4. Fine in Sent Items, broken only for recipient → EXO modern-attachment/cloud-upload issue; then compare whether 26.03 submitted a binary attachment vs 26.08 a OneDrive/cloud one (paperclip vs cloud icon in Sent Items)
    Yes — send the ProcMon trace, with these filters
    Process is <yourapp>.exe OR OUTLOOK.EXE OR SearchIndexer.exe
    Operation is CreateFile, ReadFile, CloseFile
    Path contains <attachment filename>
    What to look for:
  5. Sharing violation / ACCESS DENIED on the attach file
  6. Short reads (EndOfFile vs requested length)
  7. Different path in 26.08 (temp staging, OneDrive ~ placeholder, \\?\ long path)
  8. Whether Outlook even opens the file (if it never does, the dialog/silent-send path diverged)
    Also worth one cheap experiment: drop FROM USER (that's what sets MAPI_DIALOG via param 7) and retest 26.08 — if silent vs UI send changes the result, we've narrowed to Outlook's compose path rather than the FWH binary at all.

Antonio,

Thank you. That was it.

I compiled mapi.c from FWH 26.03 (source\winapi\mapi.c, built with -DFLAT) and linked it ahead of fivehc64.lib, with everything else on the current FWH build. MAPI email with attachments now works again. The recipient (Exchange Online, both Windows and Mac Outlook) receives the attachment normally. With the current mapi.c, the message shows as sent in Outlook, but the recipient's attachment never downloads ("try again later").

Comparing the two files, the only change that affects behavior is the new MapiFillAddressIfEmpty(), which is applied to the originator, each recipient in MAPISENDMAIL, and MAPIADDRESS. Our call is:

DEFINE MAIL oMail ;
SUBJECT cSubj ;
TEXT cText ;
FILES cSndFile, cAttachName ;
FROM USER ;
TO MailTo
SEND MAIL oMail

TO MailTo with a single argument builds { { cEmail } }, so the new code copies the plain address into lpszAddress with no SMTP: prefix. I suspect that when Outlook receives a raw, unresolved lpszAddress, it creates a one-off recipient and changes how it encodes the message (possibly TNEF/winmail.dat), which would explain why the recipient can't open the attachment. Before this change, lpszAddress was NULL and Outlook resolved the name itself, which worked correctly.

Suggestion: only fill lpszAddress for non-Outlook clients, or add the "SMTP:" prefix when copying the name into the address. At minimum, please make it optional, since it breaks attachments with Outlook/Exchange.

For now I'll keep linking the 26.03 mapi.c. I'm happy to test a corrected version.
